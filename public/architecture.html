Architecture · open source

How a request finds the right intelligence.

Decentralised.si is a set of open-source components. At the centre is oifd, a router that runs on your own device and acts as a scheduler for intelligence. For every request it decides:

  • what kind of expertise is needed, and how much;
  • which provider should supply it;
  • how much of your context may leave the device;
  • how much cost is justified;
  • when to start a backup, when to escalate, and when to stop.

This page explains each of those decisions and links to the code that makes it.

01

The principle

Find the cheapest and fastest provider that still meets the required quality floor. Then escalate only if more intelligence is actually needed.

Most AI products send every request to one large model at one company. That is simple, but it is also:

  • Expensive: a frontier model answers even simple questions.
  • Fragile: when that company has an outage, you have one too.
  • Invasive: that company sees your entire history.

Decentralised.si makes each decision per request, on your side. Three rules follow from the principle and appear throughout the code:

Quality is a floor, not a slider

A provider predicted to fall below the task's quality floor is excluded, however cheap it is. If nobody qualifies, the best available provider answers and the result is marked degraded, never passed off as meeting the target.

Every decision is explained

Each candidate gets a score broken into eight normalised components, and the selection comes with plain-language reasons. You can ask for the full decision without running any model.

The device is the source of truth

Conversation memory, the privacy mapping and learned provider statistics live on your machine. Providers receive single, pseudonymised requests. There is no central server in the decision loop.

03

Life of a request

Every request passes through the same state machine, and each transition is recorded in the task's event log. The first four steps are the fast path. They are pure in-memory work, with no network calls, no database reads and no discovery.

  1. RECEIVED
    Recall and protect

    Local conversation history is attached. Identifiers in the prompt and every context item are replaced with placeholders before anything else happens.

  2. CLASSIFYING
    Understand

    Domain, difficulty, reasoning profile, freshness and tool needs are derived from the pseudonymised text. The result is cached by a hash of the prompt.

  3. PLANNING
    Set the bar

    Mode, difficulty and your limits become a quality floor and target, a latency target, a budget, a deadline and an output-token estimate.

  4. ROUTING
    Choose

    Every provider is scored with the latest statistics from the route cache. Constraints are applied, one provider is selected and the rest are ranked as backups.

  5. STREAMING
    Answer, guarded

    Context is compiled for the chosen provider and the answer streams to you. If it is slow a backup is started; if it fails the next provider takes over.

  6. OPTIONAL_ESCALATION
    Deepen only if unsure

    Uncertainty is measured. Only if it exceeds the mode's threshold is a stronger or independent expert asked, within budget and deadline.

  7. SYNTHESIZING
    Combine

    With two answers, the most credible is kept or they are merged.

  8. COMPLETED · DEGRADED · CANCELLED · FAILED
    Record and learn

    Time to first token, latency, cost, success and escalation are written to SQLite and update the provider's statistics for that domain.

The client sees it as server-sent events:

04

Understanding the request

Domain: a taxonomy with fallback

Expertise is organised as a tree. A provider that is excellent at finance.quant.derivatives is a perfect match for an options question. A finance.quant generalist is a good match, and a generalist is an acceptable last resort.

general ├── finance banking · quant → derivatives · risk ├── technology software → rust · python · ai → inference ├── science physics · biology · chemistry ├── law corporate · tax · securities └── medicine general · cardiology · oncology finance.quant.derivatives → finance.quant → finance → general

Classification is layered:

  • Layer 1: auditable keyword rules. They take microseconds and always run. A specific domain with evidence of its own inherits its ancestors' evidence, so "Rust" plus generic software words ranks technology.software.rust above technology.software. Up to three weighted domains are kept.
  • Layer 2: a small model classifier, used only when rule evidence is weak. It sits behind the DomainClassifier trait, so a local model can replace it. It only ever sees the pseudonymised prompt, and never sees local_only requests unless it runs locally.

Difficulty: from structure, not meaning

A deterministic estimator adds up signals, and every signal is reported so the decision can be audited:

  • Raise difficulty: length, number of domains, high-stakes domains (law, medicine), explicit constraints, need for live data or calculation, multi-step and research-grade language, multi-item comparisons, jurisdiction-specific questions.
  • Lower difficulty: short definitional questions.
PromptDifficultyWhy
What is EBITDA?easyshort definitional question
Write a Rust async TCP server.mediumcode generation
Compare three tokenisation structures under Australian securities law.hardhigh-stakes domain, multi-item comparison, jurisdiction, constraint
Design a new distributed consensus mechanism and formally reason about failure modes.extremetwo research-grade cues, three multi-step cues

Difficulty moves the bar. Harder tasks raise the quality target, and the gap between strong and weak models widens: a provider's predicted quality is pulled down more on hard and extreme tasks.

05

Choosing an expert

Each provider gets eight component scores, each normalised to 0–1, so raw milliseconds and dollars are never added together. The mode decides how much each component counts.

ComponentHow it is normalised
domain matchcompetence × taxonomy factor: exact 1.0 · parent 0.85 · broader 0.65 · general 0.40 · narrower 0.70 (configurable)
predicted quality(q − floor) / (1 − floor), with q adjusted for domain fit and difficulty, blended with observed quality
latency1 / (1 + ttfi / target); the target comes from the mode, and slow providers count double
price1 / (1 + cost / (5% of budget)), from estimated input and output tokens
reliabilitycompletion reliability blended with the observed success rate, × current health
tool matchrequired tools or JSON output supported
context affinityhigher if this provider served the conversation last (its prompt cache is warm)
privacy matchlocal providers score highest; remote ones lower as the privacy class tightens

Modes

80% of the weight follows the mode. The quality share is split 60/40 between domain match and predicted quality. The other 20% is fixed: reliability 10%, tool match 5% and context affinity 5%.

Constraints before scores

Hard constraints exclude a provider outright: disabled, offline, or not allowed to see this privacy class.

Soft constraints exclude it unless nothing else qualifies: predicted quality below the floor, over budget, or too slow for the deadline. If every provider fails a soft constraint, the best reachable one answers and the task is marked DEGRADED, with the reason.

When the ideal provider is unavailable, the explanation says so. For example: quant-local is offline (best match for finance.quant.derivatives); falling back to general-local.

POST /v1/route returns the whole decision without running a model: the task vector, every candidate's components and reasons, the weights, and the timings.

06

What leaves your device

Before anything is transmitted, the prompt and every context item are scrubbed. The scrubber finds:

  • email addresses and phone numbers;
  • crypto wallets (EVM, Bitcoin, base58);
  • IBANs, card numbers (Luhn-checked) and account numbers;
  • IP addresses, and URLs that carry tokens or credentials;
  • names and other terms you tag as sensitive.

Each is replaced with a stable placeholder. The mapping stays in the daemon's memory: it cannot be serialised, and it is never logged, stored or returned by the API. Answers shown to you are rehydrated as they stream, even when a placeholder is split across chunks.

# You type (privacy: pseudonymised)
Email me at yousef@example.com and analyse this option position.

# The provider's server receives — captured on the wire
[{"role":"user","content":"Email me at <EMAIL_1> and analyse this option position."}]

# You see
… reply to yousef@example.com …
Privacy classBehaviour
publicsent as written
pseudonymiseddefault; identifiers replaced before transmission
confidentialpseudonymised, and only local or explicitly trusted providers may receive it
local_onlyremote providers are never used; if none is local, the request fails rather than leak

Minimal context, per provider

The context compiler builds a separate context for each provider:

  1. Removes duplicates.
  2. Scores each item's relevance, using its domain tag or its word overlap with the question.
  3. Drops what is unrelated, but keeps the most recent turns of the conversation.
  4. Fits the rest into that provider's context window, truncating long items head-and-tail.

A cardiology note does not travel with an options question.

07

Streaming without interruption

Hedged requests

A provider that promises a first token in 100 ms but takes 800 ms is detected while it happens. If no token has arrived after the hedge delay, the next-best provider is started. The first provider to produce a token wins, and the other request is cancelled, which closes its connection. The loser's elapsed time is recorded, so a provider that is consistently slower than it claims gets demoted.

These are real measurements from acceptance demo 4, not an illustration.

Fallback and continuation

An error before the first token moves the request to the next backup immediately.

An error after tokens have streamed is handled differently. The partial answer goes to the next provider with an instruction to continue from exactly where it stopped, and you see one uninterrupted reply with a continuing status event.

Health comes from two sources: background probes and real traffic. A refused connection marks a provider offline at once, and offline providers never receive interactive traffic.

Cancellation

DELETE /v1/tasks/:id stops everything: it aborts every provider request, stops escalation, closes the stream and records CANCELLED. Closing the connection does the same, so abandoned work never keeps consuming paid tokens.

08

More intelligence, only when needed

After each answer, oifd estimates uncertainty, from 0 to 1. It combines:

  • the provider's self-reported confidence (45%);
  • its predicted quality (15%);
  • whether the answer is complete (20%);
  • how well the provider's domain matched (10%);
  • whether required tools were missing (10%).

It climbs the ladder only while uncertainty exceeds the mode's threshold (fast 0.50, cheap 0.45, balanced 0.35, deep 0.25) and the next step fits in the remaining budget and deadline.

R1One cheap-enough expert: the scorer's pickbuilt
R2One clearly stronger expertbuilt
R3Expert plus a tool or retrieval hookinterface
R4A second, independent expert, then synthesisbuilt
R5A verifierinterface

The second opinion is chosen for diversity, not similarity: a different provider, preferably from a different model family, and with a different specialty when the question spans domains. Two copies of the same model agreeing is not evidence.

When there are two answers, the most credible one is kept (quality × completeness × confidence). Alternatively, they are merged deterministically or by a configured synthesis model.

The client sees a deepening status, then a new segment, then the result. The maximum mode always takes the R4 step.

09

Learning from outcomes

Every attempt updates that provider's statistics for the task's domain and overall. The statistics cover:

  • successes and failures;
  • average time to first token and total latency;
  • observed quality and cost.

The scorer reads them from an in-memory route cache. SQLite is written behind it by a dedicated thread, so the request path never waits on disk.

Observations are blended into the configured expectations at weight n / (n + 10), so a handful of samples nudges a provider's score without overturning it. POST /v1/tasks/:id/feedback with a rating of 1, 0 or −1 moves observed quality more strongly than passive signals do.

CREATE TABLE provider_stats (
  provider_id TEXT, domain TEXT,
  successes INTEGER, failures INTEGER,
  avg_ttfi_ms REAL, avg_total_ms REAL, avg_quality REAL, avg_cost REAL,
  last_used INTEGER,
  PRIMARY KEY (provider_id, domain)
);

Each task is also persisted as an inspectable record: classification, plan, attempts, events, timing, cost and state. It never contains the prompt or the privacy mapping. Prompts are not logged unless you switch on logging.log_prompts.

10

The hosted gateway and the network

Not every app can run a daemon, so the same ideas are also available as a hosted service at api.decentralised.si. It runs on Cloudflare Workers, and its code is in the same repository.

Drop-in APIs

Anthropic Messages, OpenAI Chat Completions, Responses and Embeddings, Gemini, and MCP. Change one base URL and keep your SDK. Streaming, tools, vision, files and batches are translated between vendors.

Blind router

Routes on a request's structure and your hints, not its meaning. It strips identity, spreads conversations across providers, and continues interrupted streams on another provider.

Accounts

Bring-your-own keys with envelope encryption, rate and spend limits, workspaces, a full console, and crypto payments.

Open provider network

Anyone can run dsi-node next to an open-weight model. The router probes it, signs its traffic and checks it with canaries. Operators earn PAI for verified work.

The two fit together naturally. The gateway speaks the OpenAI-compatible API, so oifd can use it as one more provider, next to your local models and your own keys. The daemon then decides when the gateway is the right expert, and your memory and privacy mapping stay on your machine.

Run it yourself

Install a prebuilt binary for macOS (Apple silicon or Intel), Linux (x86_64 or arm64) or Windows. The download page has one-line installers, direct downloads, checksums and background-service setup.

curl -fsSL https://decentralise.si/install/oifd.sh | sh      # macOS, Linux
irm https://decentralise.si/install/oifd.ps1 | iex          # Windows PowerShell
oifd

Or build from source with a Rust toolchain (Docker works too). The default configuration uses three simulated experts, so no GPU or API key is required to see routing work.

git clone https://github.com/Decentralised-si/Smart-LLM-Router
cd Smart-LLM-Router/oif-router
cargo run --release                       # listens on 127.0.0.1:7766

curl -N localhost:7766/v1/ask -H 'Content-Type: application/json' \
  -d '{"prompt": "Explain Black-Scholes implied volatility.", "mode": "balanced"}'

curl localhost:7766/v1/route -H 'Content-Type: application/json' \
  -d '{"prompt": "Write a Rust async TCP server."}'     # the decision, no inference

cargo test                                # 36 tests: routing, fallback, privacy, escalation, streaming
cargo run --release --bin benchmark       # overhead, TTFI, cost; CSV output

To use real models, point config/providers.yaml at any OpenAI-compatible server (vLLM, llama.cpp, LM Studio, a hosted API or the Decentralised.si gateway) or at Ollama. Declare what each one is good at:

providers:
  - id: quant-local
    endpoint: http://127.0.0.1:8101/v1
    adapter: openai                    # openai | ollama | mock
    model: quant-specialist
    domains: { finance.quant: 0.90, finance.quant.derivatives: 0.97 }
    price: { input_per_million: 0.20, output_per_million: 0.60 }
    expected_ttfi_ms: 150
    expected_quality: 0.95

The daemon binds to 127.0.0.1 and refuses any other address unless an API token is set. Provider keys are read from environment variables named in the config, never written into it.
